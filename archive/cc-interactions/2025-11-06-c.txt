  How Tags Work in Each System

  Zotero

  - Storage: Flat list of tag strings per item
  - No native hierarchy support: Zotero doesn't understand parent/child relationships
  - Search: Literal tag matching only - searching "Hotels" only finds items explicitly tagged "Hotels"
  - Tags are independent strings with no semantic relationships

  Zenodo

  - Storage: Flat keywords array
  - No hierarchy support: Similar to Zotero - just strings
  - Search: Keyword matching, no hierarchy awareness

  Omeka

  - Storage: Varies by plugin, but typically flat tags or Dublin Core Subject fields
  - Some vocabulary plugins exist: Can link to controlled vocabularies (SKOS, etc.)
  - Search: Depends on configuration, typically flat tag matching

  Two Approaches to Hierarchical Search

  Since none of these systems natively support hierarchical tags, there are two standard approaches:

  Approach 1: Tag Explosion (Write All Ancestors)

  When you tag an item with a leaf node, you ALSO write all parent/ancestor tags to the item.

  Example: Item about the Grand Hotel gets tagged with:
  - Grand Hotel (specific leaf)
  - Hotels (parent)
  - accommodation buildings (grandparent)
  - Built Environment (great-grandparent)
  - tourism & accommodation - THEMATIC (thematic parent)
  - etc.

  Advantages:
  - ✅ Simple queries work: Search "Hotels" finds all hotel items
  - ✅ No custom software needed
  - ✅ Works in any system

  Disadvantages:
  - ❌ Massive tag bloat (10-20+ tags per item vs 1 leaf tag)
  - ❌ Maintenance nightmare: If hierarchy changes, must retag all items
  - ❌ User confusion: Why does this item have "Built Environment" tag?
  - ❌ Violates clean data principle

  Approach 2: Leaf Nodes Only + Query Expansion

  Store only leaf tags on items. Maintain hierarchy separately (in your CSV/database). When users search, expand queries.

  Example: Item about Grand Hotel gets tagged with:
  - Grand Hotel (only the leaf)

  When user searches "Hotels", the search system:
  1. Reads hierarchy from tag_map_consolidated.csv
  2. Finds all children of "Hotels": Hotel, Grand Hotel, Imperial Hotel, etc.
  3. Expands query to: (Grand Hotel OR Imperial Hotel OR Hotel OR ...)
  4. Returns all matching items

  Advantages:
  - ✅ Clean item tags (leaf nodes only)
  - ✅ Hierarchy changes don't require retagging items
  - ✅ Single source of truth (the CSV)
  - ✅ Maintains intellectual clarity

  Disadvantages:
  - ❌ Requires custom search interface that understands the hierarchy
  - ❌ Can't use native Zotero/Zenodo/Omeka search without modification
  - ❌ Export to other systems loses hierarchy unless you include the CSV

  function get_all_descendants($term, $hierarchy, &$found = []) {
      // Find all direct children
      $children = $hierarchy[$term]['children'] ?? [];

      foreach ($children as $child) {
          $found[] = $child;
          // Recursive: get children of children
          get_all_descendants($child, $hierarchy, $found);
      }

      return array_unique($found); // Handle polyhierarchy
  }
